# FitOS Codebase Analysis

Phase 1, read-only. Written 2026-11-22 on branch `cloudflare-migration`.

## Summary

- The web app is a **Next.js 14 App Router** project. It builds today and is almost entirely static.
- **The web app does not talk to Supabase or to the backend.** Every screen renders hard-coded demo data or local React state.
- **All server logic lives in a separate Python FastAPI backend** (`backend/`). Cloudflare Pages cannot run it. It needs its own host, or its logic has to move.
- **There is no Vercel-specific code in the repo.** No `vercel.json`, no `@vercel/*` packages, no Vercel env vars.
- The Supabase schema has RLS on most tables, but **12 tables have none**, and the backend uses the `service_role` key, which bypasses RLS.

## 2. How the app operates

### Web app

- **Entry point:** `app/layout.tsx` wraps every page in `AppShell`, which renders the page plus a fixed 7-tab `BottomNav`.
- **Routes:** `/`, `/workout`, `/nutrition`, `/activity`, `/social`, `/social/profile/[userId]`, `/chat`, `/recovery`, `/profile`, plus `/manifest.webmanifest` generated by `app/manifest.ts`.
- **Server-side code in the web app:**
  - No API routes (`app/api/` does not exist).
  - No middleware.
  - No server actions, ISR or `revalidate`.
  - One dynamic server-rendered page: `app/social/profile/[userId]/page.tsx`. It only picks between two hard-coded athletes based on the URL.
- **Auth flow:** none. There is no login screen, no session, and no Supabase client.
- **Data flow:** none at runtime. `lib/api.ts` is a fetch wrapper for `NEXT_PUBLIC_API_BASE_URL` (default `http://localhost:8000`), but no page imports it. Pages read from `lib/demoData.ts` or inline constants.

### Backend (FastAPI)

- **Entry point:** `backend/api/main.py`. Every router is mounted twice, at `/` and at `/api/v1`.
- **Wiring:** `backend/api/deps.py` builds one `AppContainer` at startup. It creates the Supabase client with the **service_role key**, the Anthropic client, and the Open Food Facts and USDA HTTP adapters.
- **Auth:** the client sends a Supabase access token as `Authorization: Bearer`. The backend verifies it by calling `auth.get_user(token)` and uses the returned user ID. An `X-User-Id` header fallback exists but is off unless `ALLOW_DEVELOPMENT_IDENTITY=true`.
- **CORS:** only `http://localhost:3000` and `http://127.0.0.1:3000` are allowed.
- **Routes (37):** workouts, activities, nutrition (photo, barcode, search), barcode, products, food-scan, dashboard, recommendations, social, messaging, health and system.
- **Jobs:** an in-memory queue only. Jobs are lost on restart.

## 4. Supabase usage

### Where the client is initialised and how env vars are read

- **Web app:** no Supabase client. No `NEXT_PUBLIC_SUPABASE_*` variables are read anywhere.
- **Backend:** `backend/api/settings.py` reads `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` from `backend/.env` through `pydantic-settings`. The client is created in `backend/api/deps.py`.
- **No `service_role` key exists in frontend code.** No `.env` file exists in the repo, only `backend/.env.example` with empty values.

### Auth providers

None configured in code. The backend only verifies tokens. Login, signup, OAuth and magic links are not implemented anywhere.

### Tables queried by the backend

| Area | Tables |
|---|---|
| Workouts | `workouts`, `workout_exercises`, `workout_sets` |
| Activities | `activities` |
| Nutrition | `food_predictions`, `user_corrections` |
| Social | `profiles`, `follows`, `blocks`, `posts`, `comments`, `post_reactions` |
| Messaging | `conversations`, `conversation_members`, `messages` |
| Recovery | `fitness_events`, `canonical_daily_metrics`, `daily_data_status`, `daily_snapshots`, `daily_fitness_features`, `recovery_daily`, `coach_context_snapshots` |

The recovery repositories exist but are not wired into any route, so those tables are never reached through the API.

### Schema and RLS

The migrations create 48 tables.

- **Migrations 001, 003, 004, 005 and 006** enable RLS on every table they create and add at least one policy.
- **Migration 002 enables RLS on none of its 12 tables:** `exercises`, `routines`, `routine_exercises`, `foods`, `food_nutrition`, `meals`, `meal_items`, `products`, `product_nutrition`, `body_measurements`, `health_daily`, `user_feedback`. Anyone with the anon key can read and write these through the Supabase REST API.
- `docs/SUPABASE_SETUP.md` lists only migrations 001–004. Migrations 005 and 006 are missing from the apply order.

### Is RLS relied on?

Not today. The backend connects with `service_role`, which bypasses RLS, so privacy depends on Python filters. Some filters are missing:

- The social feed returns followed users' posts without checking `visibility` (`backend/repositories/supabase_social.py`, `feed`).
- Liking or commenting accepts any post ID without checking the viewer can see the post.
- User search interpolates raw input into a PostgREST `or_()` filter.

RLS becomes the real security boundary the moment the web app talks to Supabase directly with the anon key.

### Storage and Realtime

- **Storage:** no buckets, no storage policies, no upload code. Food-scan images are processed in memory only.
- **Realtime:** not used. No channels, no publications.

## 5. What will break on Cloudflare Pages or as an iOS PWA

### Cloudflare Pages

1. **The FastAPI backend cannot run on Pages.** Pages serves static files plus JavaScript Workers. The Python backend, with Pillow and `supabase-py`, needs a separate host or a rewrite. This is the biggest decision in the migration.
2. **`/social/profile/[userId]` is server-rendered.** `output: 'export'` fails on it unless it gets `generateStaticParams` or becomes a client-rendered page that reads the ID at runtime. Real user IDs are not known at build time, so the second option fits.
3. **That page types `params` as a `Promise`.** That is the Next.js 15 convention. It works on 14 by accident and should be a plain object.
4. **Backend CORS only allows localhost.** `https://fitos.pages.dev` must be added once the frontend calls the API.
5. **`.env.production` is not gitignored.** The `.gitignore` covers `.env`, `.env.local` and `.env.*.local` only.

### iOS PWA

1. **Two conflicting manifests.** `app/manifest.ts` produces `/manifest.webmanifest` pointing at `icon-192.png` and `icon-512.png`, which do not exist. `layout.tsx` links `/manifest.json` instead, which only has an SVG icon. iOS ignores SVG icons.
2. **No `apple-touch-icon`.** The home-screen icon will be a page screenshot.
3. **No service worker.** The app will not open offline and iOS treats it as a bookmark-style web app.
4. **`viewport-fit=cover` is missing** while the status bar is `black-translucent`. Content will sit under the notch and status bar.
5. **Only the bottom nav uses safe-area insets.** The top of every screen and the main padding ignore them.
6. **`maximumScale: 1` blocks pinch zoom for everyone.** That is an accessibility problem. Double-tap zoom on buttons should be fixed with `touch-action: manipulation` instead.
7. **A 7-tab bottom nav is cramped on iPhone.** Labels at 11px across 7 columns of about 55px each are hard to tap.
8. **Auth in standalone mode.** Once auth is added, iOS keeps a separate storage jar for the home-screen app. Users must sign in inside the installed app, and OAuth redirects can open Safari instead of the app.
9. **`navigator.share` with files** works in Safari 15+ but must be called directly from a tap.

## Decisions needed before Phase 2

1. **Where does the backend go?** Options:
   - **A.** Keep FastAPI and host it on a separate free service such as Render, Fly.io or Railway. The web app calls it. This matches `AGENTS.md`, but free hosts sleep when idle, so the first request is slow.
   - **B.** Have the web app talk to Supabase directly with the anon key and RLS. Move only the Claude photo scan and USDA lookups into Supabase Edge Functions. This is free, fits your Phase 4 and 5 plans, and needs no extra host. It breaks the `AGENTS.md` rule that `apps/web` never imports vendor SDKs, so that rule would need to change.
   - **C.** Do A now and decide on B later.
2. **The dynamic profile page.** I propose changing `/social/profile/[userId]` to `/social/profile?id=...`, rendered on the client. That allows `output: 'export'` with no server code.
3. **Git baseline.** The folder was not a git repo. I ran `git init` and created `cloudflare-migration` with no commits, because git has no name or email configured. Diffs need a baseline commit of the current code before Phase 2.
